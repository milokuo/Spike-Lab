> Iteration goal: address six owner playtest notes on top of the working M2 vertical
> slice — slower/clearer ball, real jump kinematics, a code-based lobby with 2v2,
> a behind-the-back follow camera, taller gameplay-relevant scale, and a held-ball
> serve presentation. Backward compat is **not** required (§f): no deployed users,
> so the wire protocol may break freely.

## a. Charge Audit Findings

**Question:** is the ×1.6-at-full-charge distance multiplier (§6.2) wired end-to-end
from client hold duration → `TouchIntent.charge` → server `BallLaunch` velocity?

**VERDICT: WIRED and correct for rally touches.** Full trace (all present in current code):

1. `client/input/keyboard.ts` — J/K/L **press** records `pressedAtMs` + `dirInput`
   (§5.1 sampling). **Release** computes `charge = min(1, heldSeconds * CHARGE_RATE)`
   with `CHARGE_RATE = 0.8` and emits `RawTouchEvent { charge }`. ✔ hold→charge.
2. `client/main.ts` `wireRoom()` — `keyboard.onTouch` → `sendTouch({ …, charge: touchEvent.charge })`
   → `TouchIntent.charge`. ✔ charge crosses the wire.
3. `server/rooms/MatchRoom.ts` `handleRallyTouch()` — passes `charge: intent.charge`
   into `buildBallLaunch`. ✔ server consumes it.
4. `shared/ballistics/launch.ts` `buildBallLaunch()` — `speedMult = chargeDistanceMult(charge)`
   = `1 + 0.6*charge`; `velocity = direction * baseSpeed * speedMult`. ✔ ×1.6 at c=1.

**Gaps / bugs found (not blocking, but fix in M2.1):**

- **G1 — Serve ignores charge.** `handleServe()` hardcodes `charge: 0, quality: 1`, so
  spec §9 "跳發可蓄力/球速較快" is not honored. Serve is always the same speed.
- **G2 — Charge scales the WHOLE velocity vector, including Y.** In `buildBallLaunch`,
  `velocity.y = direction.y * speed * heightFactor` where `speed` already includes the
  charge multiplier. Spec §6.2 says charge affects *distance only*. Consequence: a
  charged set flies both farther **and** higher. Acceptable for a parabola (higher +
  faster ≈ farther) but note it when retuning; it is why charged shots feel extra
  floaty-fast today. **Decision: leave the coupling (simplest, still monotonic in
  distance) but lower base speeds so the effect is smaller in absolute terms.**
- **G3 — Timing-vs-charge conflict (design risk, not a wiring break).** The touch is
  *adjudicated* at the **press** instant (`clientTime = pressedAtMs`, dirInput sampled at
  press) but the `BallLaunch` only fires on **release** after up to ~1.25 s of hold. The
  server rewinds the ball to press-time, so a "PERFECT at press" can be charged and fired
  long after the ball has physically left. This is inherent to charge-by-hold + a timing
  window. **Kept as-is for M2.1** (changing it is a §6 手感 redesign); flagged for the
  orchestrator as the one place charge and timing genuinely fight.

**Root cause of "ball too fast":** `SPIKE_BASE_SPEED = 14` u/s uncharged (→ 22.4 at full
charge) on an 18-unit court means the ball crosses the whole court in well under a
second. Uncharged is already at the old "too fast" ceiling, so charge adds nothing
*legible*. Fix = lower baselines so uncharged is controllable and full-charge recreates
the punchy fast ball only when earned (see §b retune table).

## b. Shared Contract & Constant Changes

All new/changed definitions live in `packages/shared/src` and are re-exported from the
barrel `index.ts`. Server and client implement only against these.

### b.1 Retuned base speeds (feedback #1)

`DIG_BASE_SPEED`/`SET_BASE_SPEED` currently live as private consts in
`intent/direction.ts`; **move them into `constants.ts`** so all speeds are in one table.

| Constant | Old | New | Rationale |
|---|---|---|---|
| `SPIKE_BASE_SPEED` | 14 | **9** | Uncharged spike controllable; full charge → 14.4 recreates the old "fast" ball only when earned. Clearly distinguishable. |
| `DIG_BASE_SPEED` | 6 | **4.5** | Softer bump; dig is a control touch, not a weapon. |
| `SET_BASE_SPEED` | 7 | **5.5** | Loftier/slower set so the receiver has time to line up a spike. |
| `SERVE_BASE_SPEED` | (n/a, reused spike 14) | **8** (new) | Serve gets its own baseline; fixes G1 by decoupling from spike. |
| `CHARGE_DISTANCE_MULT_SLOPE` | 0.6 | **0.6** (unchanged) | Spec §6.2 locks ×1.6 at full charge — this is the realism anchor, don't touch. |

> Effect: full-charge spike 9→14.4 (−36% vs old uncharged), uncharged spike 14→9 (−36%).
> The *ratio* charged:uncharged is fixed at 1.6 by spec; we win legibility by dropping the
> absolute floor.

### b.2 Scale constants — now GAMEPLAY constants in shared (feedback #5)

Player height currently lives only in `client/scene/player.ts` (capsule 1.2 + 2×0.35 =
1.9 u). Promote to shared because touch-reach and future blocking depend on it. Court
18×9 and net 2.43 stay **fixed** (spec realism anchor).

| Constant (new in `constants.ts`) | Value | Note |
|---|---|---|
| `PLAYER_HEIGHT` | **2.0** | Standing head height (realistic pro ~2.0 m). Taller than old 1.9. |
| `ARM_REACH` | **0.55** | Hand height above head when reaching up. |
| `STANDING_REACH` | **= PLAYER_HEIGHT + ARM_REACH = 2.55** | ≈ net 2.43 → can just touch net standing (realistic), jump gives clearance. |
| `TOUCH_VERTICAL_MARGIN` | **0.3** | Slack on the new vertical reach gate (§b.5). |
| `JUMP_MAX_HEIGHT` (derived, see §c) | **≈1.10** | Full-charge foot apex → hand apex `STANDING_REACH + 1.10 = 3.65` **≫ 2.43** (margin 1.22). |

Client `scene/player.ts` capsule is rebuilt from `PLAYER_HEIGHT`/`ARM_REACH` (visual =
gameplay). Net/court meshes already read shared constants — unchanged.

### b.3 Jump constants (feedback #2) — replaces old floaty `JUMP_HEIGHT`/`JUMP_HANG_S`

Remove `JUMP_HEIGHT = 1.4`, `JUMP_HANG_S = 0.7` (they drove the ad-hoc client-only integrator).

```ts
export const JUMP_GRAVITY   = 18;    // units/s^2 for the character (snappier than ball GRAVITY 9.8)
export const JUMP_V0_MIN    = 4.0;   // tap: apex = v0^2/(2g) ≈ 0.44 u
export const JUMP_V0_MAX    = 6.3;   // full charge (hard cap): apex ≈ 1.10 u
export const JUMP_CHARGE_RATE = 1.5; // per second → full charge in ~0.67 s of holding Space
export const JUMP_STAMINA_MIN = 6;   // tap cost
export const JUMP_STAMINA_MAX = 12;  // full-charge cost (higher jump costs more, §7.1 baseline was 8)
```

### b.4 Protocol change — charged jump command (feedback #2)

`InputFrame.jump: boolean` is replaced by a discrete, charged command that is non-null
**only on the frame a jump is initiated** (fired on Space release, mirroring J/K/L charge).
This structurally guarantees "exactly one stamina charge per jump" (fired once) and "no
air jump" (server ignores when airborne).

```ts
// types/messages.ts
export interface JumpCommand {
  charge: number; // 0..1 hold duration, sampled at Space release
}

export interface InputFrame {
  seq: number;
  clientTime: number;
  move: { x: Axis; y: Axis };
  jump: JumpCommand | null;   // was: jump: boolean. Non-null ONLY on the initiating frame.
  dtMs: number;
}
```

> Vertical integration is NOT tied to input frames: both ends run `integrateJump` every
> tick/frame (gravity keeps pulling even when no InputFrame arrives), so an idle airborne
> player still lands. `jump` only seeds the initial velocity.

### b.5 Vertical touch reach gate (feedback #5 consequence)

Today `lagComp.adjudicateTouch` gates on **horizontal** `distXZ ≤ REACH_MAX (1.8)` only —
height is ignored, so scale has no gameplay effect yet. Add a vertical gate so a ball far
above a grounded player is unreachable but a jumping player can meet it:

```ts
// shared/quality/fDistance.ts (or a small reach.ts) — pure
export function isWithinVerticalReach(
  ballY: number, playerY: number, jumpY: number
): boolean; // ballY <= playerY + STANDING_REACH + jumpY + TOUCH_VERTICAL_MARGIN
```

Server passes the toucher's rewound `jumpY` (from player history, now including Y) into
this gate alongside the existing horizontal gate. This is the hook blocking will reuse.

### b.7 Teammate-targeted dig for 2v2 (feedback #3, §5.1)

`intent/direction.ts` `IntentInput` currently has no teammate data, so `resolveDig` always
uses the 1v1 self-set fallback. Change:

```ts
export interface IntentInput {
  mode: Mode;
  dirInput: { x: Axis; y: Axis };
  charge: number;
  toucherPos: Vec3;
  toucherSide: Side;
  teammates?: Vec3[];   // NEW: positions of same-side OTHER players (empty/undefined in 1v1)
}
```

`resolveDig`: if `teammates` is non-empty, loft the ball toward the **nearest teammate**
(§5.1 "推向最近的隊友"); otherwise keep the existing self-set fallback. Server supplies
teammate positions from `state.players`. Everything else in §5.1 is unchanged.

## c. Jump Kinematics Spec (feedback #2)

New pure module `packages/shared/src/kinematics/jump.ts` — **identical code on server sim
and client prediction**, eliminating the current rubber-band (see §e risk).

```ts
export interface JumpState { y: number; vy: number; grounded: boolean; }

// charge 0..1 → initial vertical velocity, clamped to [V0_MIN, V0_MAX] (hard cap).
export function jumpChargeToV0(charge: number): number;

// foot apex height for a given charge = v0^2 / (2 * JUMP_GRAVITY).
export function jumpApexHeight(charge: number): number;

// stamina cost, monotonic in charge: JUMP_STAMINA_MIN + (MAX-MIN)*clamp01(charge).
export function jumpStaminaCost(charge: number): number;

// Grounded-gated jump start: if grounded → { vy: v0, grounded:false }; else NO-OP (no air jump).
export function startJump(state: JumpState, charge: number): JumpState;

// Fixed-step vertical integration (call every tick/frame): vy -= g*dt; y += vy*dt;
// on y<=0 → land: { y:0, vy:0, grounded:true }. Pure; returns a new state.
export function integrateJump(state: JumpState, dtMs: number): JumpState;
```

- **Kinematics:** `v0 = jumpChargeToV0(charge)`; apex `= v0²/(2g)`; hang `= 2·v0/g`.
  Tap: v0=4.0 → apex 0.44 u, hang 0.44 s. Full: v0=6.3 → apex 1.10 u, hang 0.70 s.
- **Hard cap:** apex never exceeds `jumpApexHeight(1) ≈ 1.10 u` (clamp on v0).
- **One stamina charge per jump:** cost is deducted exactly once, at `startJump` on the
  release frame — never per-tick.
- **No air jump:** `startJump` is a no-op unless `grounded`. Server is authoritative;
  client mirrors the same gate so prediction agrees.
- **Reach check:** full-charge hand apex = `STANDING_REACH (2.55) + 1.10 = 3.65 ≫ net 2.43`
  (clearance 1.22 u) — a jumping player's reach clearly beats the net (§5 requirement).

Tests (WP1): apex/hang for tap & full; hard-cap clamp at charge>1; monotonic stamina cost;
`startJump` no-op while airborne; `integrateJump` lands exactly at y=0; determinism
(same inputs → identical `JumpState` across two runs).

## d. Lobby Design (feedback #3)

**Style decision: room CODE (not a public list).** Justification: zero matchmaking/list
infrastructure, works identically on LAN now and over the internet later, and matches a
friend-group party game — one person hosts, drops the code in a chat, friends paste it.
We reuse **Colyseus's built-in `room.roomId`** as the code (already short & random), so
there is *no* custom code-generation or collision handling.

**Colyseus flow:**

- `gameServer.define(ROOM_NAME, MatchRoom)` — one room type, `maxClients = 4`.
- **Create:** `client.create(ROOM_NAME)` → read `room.roomId` → show it as the code.
  First joiner is `hostId`.
- **Join:** `client.joinById(code)`. Colyseus rejects a full/locked room → client shows
  "room full / not found".
- Room `autoDispose` when empty (default).

**Team assignment — auto-balance.** On join, seat the player on the side with fewer
players (tiebreak A). No side-picking UI (non-technical friends). Roster + teams shown in
the waiting room; the host may leave teams as-is.

**Start / size.** Room holds up to 4. Host sees a **Start** button, enabled when
`canStart` (≥2 players AND each side ≥1). Match size is derived at start: 2 players → 1v1,
4 → 2v2 (3 → short-handed 2v1, allowed). On `CH.START_MATCH` from the host, phase
`'lobby' → 'serve'`.

**Player leaving mid-match — simple policy:**
- **In lobby:** just remove the slot; if the host left, promote the lowest-seat remaining
  player to host.
- **In match, side still has ≥1 player:** keep playing short-handed, no pause (2v2 → 2v1).
- **In match, a side becomes empty:** end immediately → `phase = 'gameover'`, surviving
  side wins by forfeit (`DeathEvent`-style gameover broadcast).
- **No reconnection window** in M2.1 (out of scope; keep simple).

**Client UI states (minimal DOM over the canvas):**
```
MENU ──create──▶ WAITING(host, shows code + roster + Start)
  │                    │ start
  └──join(code)──▶ WAITING(guest, shows roster) ──▶ IN_GAME ──gameover──▶ GAMEOVER(rematch → WAITING)
```
`LobbyState` drives WAITING; existing `StateSnapshot` drives IN_GAME; `hud` gains a small
lobby panel. Name entry (`CH.SET_NAME`) is a text field on MENU (defaults to "Player N").

## f. Backward-Compatibility Note

No deployed users → **the old protocol may break entirely.** `InputFrame.jump` changes
type (boolean → `JumpCommand | null`), `MatchPhase` gains `'lobby'`, new channels and
lobby/name fields are added, and base-speed/scale/jump constants change values. We do
**not** add versioning, migration shims, or dual-read paths. Client and server ship
together; the only compatibility contract is "both built from the same `@spike/shared`".

Camera constants (feedback #4) are **client-only** (`packages/client/src/config.ts`) — not
part of the shared gameplay contract — and carry inline `// tuning margin` comments so the
owner can nudge pitch/offset without touching gameplay code.
